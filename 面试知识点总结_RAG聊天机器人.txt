【P1】deepseek-r1 思考模型流式输出"假死"
================================================================================

1. 说明问题 + 错误代码
-----------------------------------------------
问题：用户在前端提问后，界面干等 1.5~2 分钟没有任何输出，像是卡死/报错。

错误代码（postger_reserve_chat.py 原始 generate）：
    async for line in response.aiter_lines():
        ...
        if "message" not in chunk_data:
            continue
        token = chunk_data["message"].get("content", "")   # ← 只读 content
        full_response += token
        yield {"event": "message", "data": json.dumps({"token": token, ...})}

2. 现象
-----------------------------------------------
- 探测后端 /chat/stream 实测：HTTP 200 在 1.4s 返回，但思考阶段 256 个 chunk 的
  content 全是空字符串，首个非空 token 要等到 97.6 秒才出现。
- 前端 chat_with_stream 里 `if token:` 为 False → 跳过更新 → UI 一直空白。
- 用户感知：提问后界面 1~2 分钟无反应，判定为"卡死/报错"。
- 实际上没有任何异常抛出（无 error 事件、无 Traceback），是"静默卡顿"。

3. 原理
-----------------------------------------------
deepseek-r1:7b 是「思考模型（reasoning model）」。Ollama 流式（/api/chat stream=true）
返回的每个 chunk 的 message 字典有 3 个字段：
    {"role":"assistant", "content":"", "thinking":"好的，让我想想..."}
- thinking 字段：思考过程的文字（先输出，占大部分时间）
- content 字段：最终正式回答（思考结束后才输出）

实测比例：316 个 chunk 中 253 个是 thinking（content 为空），仅 62 个有 content。
原始代码只读 message.content，思考阶段全程拿到空串，所以一个 token 都不下发。

【名词解释：思考模型 / Chain-of-Thought】
思考模型在给出答案前，先在内部做"思维链（Chain-of-Thought, CoT）"推理，
把推理过程显式输出（而非黑盒）。代表：DeepSeek-R1、OpenAI o1/o3、QwQ。
好处：复杂推理任务准确率更高；代价：耗时长、token 消耗大。

4. 解决
-----------------------------------------------
后端（postger_reserve_chat.py）：同时读 thinking 字段，只下发有实质内容的事件
    msg = chunk_data["message"]
    token = msg.get("content", "")
    thinking = msg.get("thinking", "")        # 新增
    full_response += token                     # 只累计 content 存库
    full_thinking += thinking                   # thinking 不存库，仅前端展示
    if token or thinking:                       # 跳过空事件，减少 256 次无效下发
        yield {"event":"message",
               "data": json.dumps({"token": token, "thinking": thinking, "done":...})}

前端（web.py）：用 Gradio 6.x 的 reasoning_tags 把 thinking 包进 <thinking> 标签
    chatbot = gr.Chatbot(..., reasoning_tags=[("<thinking>", "</thinking>")])
    # build_content 把思考包进标签，Gradio 自动抽成可折叠的「Reasoning」块
    def build_content(thinking, answer):
        if thinking:
            return f"<thinking>{thinking}</thinking>{answer}"
        return answer

修复后效果：思考阶段实时展示推理过程（折叠区），不再干等。
注意：存库的 full_response 只含 content，不含 thinking（避免历史污染）。

【P2】Gradio 流式 UI 不刷新（浅拷贝问题）
================================================================================

1. 说明问题
-----------------------------------------------
chat_with_stream 里直接就地修改 history 列表里的 dict，yield 同一个引用，
Gradio 检测不到变化，UI 不刷新。

错误代码：
    history[-1]["content"] = full_answer
    yield history                            # ← 返回同一个 list 引用

2. 现象
-----------------------------------------------
后端 SSE 正常下发 token，但前端气泡一直空白，直到流结束后才一次性显示。

3. 原理
-----------------------------------------------
Gradio 判断是否需要重渲染，依赖"输出对象的引用是否变化/是否是新对象"。
就地修改 list 内部元素（改 dict 的 value）不改变 list 本身的 id，
Gradio 的 diff 机制认为没变化，跳过重渲染。

【名词解释：引用相等 vs 值相等】
Python 中 list 是可变对象，a = [{}]; b = a; b[0]["x"]=1 后 a 也变了（同一对象）。
Gradio 用 id()/引用比较，不是值比较。必须返回"新对象"才能触发更新。

4. 解决
-----------------------------------------------
每次 yield 前做浅拷贝，返回新 list + 新 dict：
    def snapshot(h):
        return [dict(m) for m in h]          # 新 list，每个 dict 也是新的
    ...
    yield snapshot(history)

【P3】SQLAlchemy 向量类型参数绑定语法错误（:v::vector）
================================================================================

1. 说明问题
-----------------------------------------------
retriever.py 里写 pgvector 相似度查询，用 :v::vector 报语法错误。

错误代码：
    sql = text("SELECT ... 1 - (embedding <=> :v::vector) AS score ...")

2. 现象
-----------------------------------------------
    sqlalchemy.exc.ProgrammingError: (psycopg2.errors.SyntaxError)
    错误: 语法错误在 ":" 或附近
    LINE 1: ...VALUES (..., :v::vector)

3. 原理
-----------------------------------------------
SQLAlchemy 的 text() 用 :name 做"命名参数占位符"（bind parameter），
它会把 :v 替换成 %(v)s（psycopg2 风格）再交给驱动。
而 PostgreSQL 的类型转换语法是 value::type，这里的 :: 和 :v 占位符冲突——
SQLAlchemy 把 :v::vector 解析时遇到第二个 : 混乱，导致语法错误。

【名词解释：SQLAlchemy bind parameter】
text("...WHERE id=:uid") 中 :uid 是命名占位符，SQLAlchemy 自动转义防 SQL 注入，
绝不能用字符串拼接拼 SQL（有注入风险）。

4. 解决
-----------------------------------------------
用 CAST(:v AS vector) 代替 ::vector，避免 :: 与占位符冲突：
    sql = text("""
        SELECT ..., 1 - (embedding <=> CAST(:q AS vector)) AS score
        FROM document_chunks
        ORDER BY embedding <=> CAST(:q AS vector)
        LIMIT :k
    """)
    conn.execute(sql, {"q": str(q_emb), "k": k})

【P4】变量名遮蔽导致 'str' object is not callable
================================================================================

1. 说明问题
-----------------------------------------------
ingest.py 里函数参数名 text 遮蔽了顶部 from sqlalchemy import text。

错误代码：
    from sqlalchemy import text
    def ingest_document(doc_id, text):       # ← text 参数遮蔽了 sqlalchemy.text
        ...
        conn.execute(text("INSERT ..."))     # ← 这里 text 是传入的字符串，不可调用

2. 现象
-----------------------------------------------
    TypeError: 'str' object is not callable

3. 原理
-----------------------------------------------
Python 函数内局部变量（含参数）会遮蔽（shadow）外层同名名字。
参数 text 是字符串，函数体内 text 指向这个字符串，不再是 sqlalchemy 的 text 函数，
所以 text("...") 调用字符串就报 'str' object is not callable。

【名词解释：作用域遮蔽 shadowing】
内层作用域的名字会"遮住"外层同名名字。常见坑：模块名与变量名冲突
（如 import math; math = 0 后 math.sin 报错）。命名应避开内置/已导入名。

4. 解决
-----------------------------------------------
参数改名 doc_text：
    def ingest_document(doc_id, doc_text):  # 不再遮蔽 sqlalchemy.text
        ...
        conn.execute(text("INSERT ..."), {...})

【P5】IVFFlat 索引小数据集召回为空 → 换 HNSW
================================================================================

1. 说明问题
-----------------------------------------------
document_chunks 表数据量少（几十条）时，IVFFlat 索引检索返回空，RAG 失效。

2. 现象
-----------------------------------------------
上传文档切块入库后，检索 top-k 总是空，LLM 拿不到参考资料，降级为纯对话。

3. 原理
-----------------------------------------------
【IVFFlat】把向量空间分成 lists 个聚类簇，查询时只扫 probes 个最近的簇。
- 必须先有足够数据训练聚类中心（lists 一般设 √N）。
- 数据少时聚类没意义，且 probes 设小易漏召回（边界向量落在别的簇）。
- 需手动调 lists/probes，对数据量敏感。

【HNSW】Hierarchical Navigable Small World，分层可导航小世界图索引。
- 基于图的多跳近邻搜索，无需训练，插入即生效。
- 召回率高且稳定，对小数据集也友好。
- 代价：建图慢、内存占用大；查询无需调 probes。

4. 解决
-----------------------------------------------
schema.sql 用 HNSW + 余弦算子类：
    CREATE INDEX IF NOT EXISTS idx_chunks_embedding
        ON document_chunks USING hnsw (embedding vector_cosine_ops);

【K1】SSE（Server-Sent Events）流式通信
================================================================================

1. 在哪里用的
-----------------------------------------------
后端 FastAPI（sse_starlette.EventSourceResponse）→ 前端 Gradio（requests stream）。

2. 为什么用它
-----------------------------------------------
LLM 流式生成 token，需要"边生成边下发"而非等全部生成完再返回。
SSE 是 HTTP 长连接、服务端单向推送、文本协议，比 WebSocket 轻量，
天然适合"服务端推、客户端只读"的流式输出场景（LLM token 流）。

3. 协议格式要点
-----------------------------------------------
  event: message          # 事件类型
  data: {"token":"你好"}  # 数据行
  (空行分隔一个 event)
  : ping - ...            # 冒号开头是注释，sse_starlette 用来保活

客户端解析：先按行读，event: 行定类型，data: 行取数据，遇到空行结束一个事件。

4. 替代方案
-----------------------------------------------
- WebSocket：双向，但 LLM 场景只需单向推送，过重。
- chunked transfer + NDJSON：Ollama 原生 /api/chat stream 就是 NDJSON（每行一个 JSON），
  但前端没有 event 分类型的能力，SSE 的 event 字段能区分 message/done/error 更清晰。
- gRPC stream：强类型但浏览器支持差，不适合 Gradio 前端。

【K2】Gradio 6.x Chatbot messages 格式 + reasoning_tags 思考折叠
================================================================================

1. 在哪里用的
-----------------------------------------------
前端 web.py 的 gr.Chatbot 组件。

2. 为什么用它
-----------------------------------------------
- type="messages"（6.x 默认）：历史用 [{"role":"user","content":"..."}] 字典格式，
  对齐 LLM 的 messages 结构，可直接喂给 Ollama/OpenAI。
- reasoning_tags=[("<thinking>","</thinking>")]：扫描消息 content 里的
  <thinking>...</thinking> 标签，自动抽成可折叠的「Reasoning」块展示。
  专配 deepseek-r1/o1 等思考模型，思考过程实时折叠展示，答案正常显示。

3. 工作原理
-----------------------------------------------
Gradio 后处理时调 _extract_thinking_blocks(content, tags)：
  - 按标签把 content 切成 (text, is_thinking, status) 段
  - thinking 段 → 生成 metadata={"title":"Reasoning"} 的独立消息（折叠块）
  - 非 thinking 段 → 正常消息
所以 content="<thinking>推理</thinking>答案" 会渲染成「折叠推理块 + 答案」。

4. 关键坑
-----------------------------------------------
- 流式时每次 yield 的 content 都会被重新解析，所以 <thinking> 标签必须闭合
  （thinking 进行中也要提前写 </thinking>），否则解析不出折叠块。
- 6.x 不再支持 tuple/list 格式的历史，必须统一 messages 字典格式，
  否则报 "Data incompatible with messages format"。

【K3】pgvector + HNSW 向量相似度检索原理
================================================================================

1. 在哪里用的
-----------------------------------------------
src/rag/retriever.py：把用户问题向量化后，pgv_search 取 top-k 最相似文档块。

2. 为什么用它
-----------------------------------------------
PostgreSQL 装 pgvector 扩展后能存向量、做相似度检索，无需另起一个向量库
（Milvus/Qdrant），运维简单。RAG 的核心就是"语义相似检索"。

3. 核心概念
-----------------------------------------------
- embedding：文本→高维向量（本项目 nomic-embed-text，768 维）。语义相近的文本向量靠近。
- 距离算子（pgvector 提供 3 种）：
    <=>  余弦距离（最常用，对文本语义最稳）   本项目用这个
    <->  欧氏距离
    <#>  负内积
- score = 1 - (embedding <=> q)  把余弦距离转成相似度（0~1，越大越相似）。
- HNSW 索引 + vector_cosine_ops 算子类：加速 <=> 查询，否则全表扫描 O(N)。

4. 完整 SQL
-----------------------------------------------
    SELECT dc.id, dc.content, d.title,
           1 - (dc.embedding <=> CAST(:q AS vector)) AS score
    FROM document_chunks dc
    LEFT JOIN documents d ON d.id = dc.doc_id
    WHERE dc.embedding IS NOT NULL
    ORDER BY dc.embedding <=> CAST(:q AS vector)   -- 按距离升序=最相似在前
    LIMIT :k

5. 替代方案
-----------------------------------------------
- Faiss（内存级，快但不持久化，要自己管存储）
- Milvus / Qdrant / Weaviate（专业向量库，大规模更优，但多一个服务）
- 本项目数据量小，pgvector 够用且与业务库统一，无需引入额外组件。

【K4】deepseek-r1 思考模型（reasoning model）输出结构
================================================================================

1. 在哪里用的
-----------------------------------------------
后端调用 Ollama /api/chat，模型 deepseek-r1:7b（qwen2 架构，Q4_K_M，4.7GB）。

2. 流式输出结构
-----------------------------------------------
每个 chunk：
    {"model":"deepseek-r1:7b",
     "message":{"role":"assistant","content":"答案token","thinking":"思考token"},
     "done":false}
最后一块：
    {"message":{"role":"assistant","content":""},"done":true,
     "done_reason":"stop","total_duration":..,"prompt_eval_count":..,"eval_count":..}

3. 关键指标
-----------------------------------------------
- prompt_eval_count：输入 prompt 的 token 数
- eval_count：生成的 token 数（含 thinking + content）
- load_duration：模型载入耗时（冷启动几十秒，热启动<1s）
- thinking 阶段：占大部分 eval 时间，content 为空
- 模型默认 5 分钟空闲后卸载（OLLAMA_KEEP_ALIVE），首次请求要重载

4. 工程注意
-----------------------------------------------
- 超时设大：思考模型单次可能 1~2 分钟，httpx timeout 设 300s，前端 600s。
- 限制历史长度：发给 LLM 的历史只取最近 N 条（DB 存全量），否则 prompt 膨胀、
  prompt_eval 暴增、首 token 极慢。
- 存库只存 content（正式答案），thinking 不入库。

【K5】httpx 异步流式 vs requests 同步流式
================================================================================

1. 在哪里用的
-----------------------------------------------
- 后端：httpx.AsyncClient（async/await，配合 FastAPI 异步）
- 前端：requests（Gradio 的生成器是同步的，用 requests stream）

2. 区别
-----------------------------------------------
httpx.AsyncClient:
    async with httpx.AsyncClient(timeout=300) as client:
        async with client.stream("POST", url, json=payload) as resp:
            async for line in resp.aiter_lines():   # 异步逐行
- 事件循环友好，一个 worker 能并发处理多个请求，不阻塞。
- FastAPI 异步端点必须用 async 客户端，否则阻塞事件循环。

requests:
    resp = requests.post(url, params=..., stream=True, timeout=600)
    for line in resp.iter_lines(decode_unicode=True):   # 同步逐行
- 阻塞式，简单直观，适合 Gradio 同步生成器。
- Gradio 的生成器函数是同步的，内部用 yield，不能用 async。

3. 替代方案
-----------------------------------------------
- aiohttp：async 客户端，httpx 的同类替代，API 风格不同。
- httpx 同步模式：httpx.Client（如果想统一 httpx 库）。

【K6】FastAPI + sse_starlette 流式响应机制
================================================================================

1. 在哪里用的
-----------------------------------------------
后端 /chat/stream 端点。

2. 为什么用它
-----------------------------------------------
FastAPI 端点是 async def，return 一个 StreamingResponse/EventSourceResponse，
FastAPI 把它当流式响应处理：先发 200 + headers，再逐个 yield body。
sse_starlette.EventSourceResponse 自动按 SSE 协议格式化（event:/data: 行），
还会定期发 : ping 保活，防止代理超时断连。

3. 关键机制
-----------------------------------------------
- 函数体内 await RAG 检索完成后，才 return EventSourceResponse(generate())
  → 即 RAG 完成前不会有任何响应（headers 都没发）。
- generate() 是 async generator，yield {"event":..,"data":..} 逐事件下发。
- 注意：sse_starlette 的 ping 在 EventSourceResponse 返回后才开始，
  所以"看到 ping"说明已过了 RAG、进入 Ollama 流式阶段。

4. 替代方案
-----------------------------------------------
- FastAPI 自带 StreamingResponse：需自己拼 SSE 格式字符串，麻烦。
- 直接 Ollama 的 NDJSON：前端要自己解析，没有 event 类型区分。

【K7】RAG 检索增强生成完整链路
================================================================================

1. 在哪里用的
-----------------------------------------------
postger_reserve_chat.py 的 /chat/stream + src/rag/* 模块。

2. 完整链路
-----------------------------------------------
【入库阶段】
  上传文件 → read_file 提取文本 → chunk_text 固定窗口切块(带 overlap)
  → 逐块 embed（nomic-embed-text 768维）→ 入 document_chunks 表(含 embedding 向量)

【检索阶段】
  用户问题 → embed(query) 向量化 → pgvector HNSW 检索 top-k 块
  → 拼成 system prompt："你是知识库助手，依据以下资料回答…【参考资料】{chunks}"

【生成阶段】
  system + 历史(最近N条) + 用户问题 → Ollama deepseek-r1 流式生成
  → SSE 逐 token 下发前端 → 存库(只存 content)

3. 为什么用 RAG
-----------------------------------------------
- LLM 知识有截止日期、不知私有数据；RAG 把外部知识注入 prompt，无需微调。
- 比微调便宜、可即时更新（删/加文档即可）、答案可溯源（引用检索到的块）。
- 适合企业知识库、文档问答、客服等场景。

4. 关键工程点
-----------------------------------------------
- 切块策略：固定窗口+overlap，避免切断语义；chunk_size 权衡（太小丢上下文，太大稀释）。
- 检索降级：RAG 失败时降级为纯对话，不阻断聊天（try/except 返回 []）。
- prompt 注入位置：system 消息插在 history 最前，确保 LLM 当作指令遵循。
- 历史窗口：DB 存全量历史，发给 LLM 只取最近 N 条，控制 prompt 长度。

================================================================================
高频面试问题速答（本项目相关）
================================================================================

Q: 流式输出为什么用 SSE 而不是 WebSocket？
A: LLM 场景是服务端单向推送 token，SSE 轻量、基于 HTTP、自动重连、
   浏览器原生支持；WebSocket 是双向、握手更重，单向推送场景用 SSE 更合适。

Q: Gradio 流式更新 UI 的关键是什么？
A: 每次 yield 必须返回"新对象"（浅拷贝 list + dict），否则 Gradio 引用比较
   判定无变化、跳过重渲染，表现为 UI 不刷新。

Q: 向量检索用余弦相似度还是欧氏距离？
A: 文本语义检索用余弦（cosine），只看方向不看模长，对文本长度不敏感。
   pgvector 里 <=> 是余弦距离，score = 1 - distance。

Q: HNSW 和 IVFFlat 怎么选？
A: 数据量大且要控制内存/建图时间可选 IVFFlat（需调 lists/probes）；
   小数据集或要稳定召回选 HNSW（无需训练、召回高、但内存占用大）。
   生产推荐 HNSW，省心。

Q: SQLAlchemy 怎么防 SQL 注入？
A: 用 text() + 命名参数（:name），SQLAlchemy 自动转义成驱动占位符
   (psycopg2 的 %(name)s)，绝不字符串拼接。向量类型转换用 CAST(:v AS vector)
   而非 :v::vector（:: 会和参数占位符冲突）。

Q: 思考模型（deepseek-r1）和普通模型的流式输出有什么不同？
A: 思考模型先输出 thinking（推理过程，content 为空），再输出 content（答案）。
   后端要读 message.thinking 字段，否则思考阶段全程拿不到 token、前端假死。
   存库只存 content，thinking 仅前端展示。

Q: RAG 中为什么要限制发给 LLM 的历史长度？
A: DB 存全量历史用于回溯，但发给 LLM 只取最近 N 条。历史过长会导致
   prompt_eval 暴增、首 token 极慢、context 超限，思考模型尤其敏感。

Q: httpx AsyncClient 为什么不能在 Gradio 前端用？
A: Gradio 的生成器是同步的（用 yield，非 async），同步生成器里不能 await。
   所以后端用 httpx 异步（FastAPI async 端点），前端用 requests 同步流式。
